## 2. 判定（关键区分）

| 观测 | 含义 |
|---|---|
| **枚举成功**（`viFindRsrc` 列出 GPIB0::9） | 枚举**不碰硬件**，只走 IO Libraries 的配置/缓存 → 只证明"配置还在" |
| **`viOpen` 抛 C++ 异常 + 进程访问违例（0xC0000005）** | 打开会话**要真的碰接口** → 说明 **`ioGPIB` 层的接口状态已损坏**；若是"被占用"应是 `VI_ERROR_RSRC_BUSY`，不会是崩溃 |
| 杀掉所有可疑持锁/卡死进程后**仍失败** | **不是句柄泄漏、不是咨询锁、不是别的进程占着** |
| 拔插 USB 只让"枚举"恢复 | 重新枚举 ≠ 重新初始化 Keysight 接口处理器/内核驱动段 |
| `pnputil /restart-device` 要求重启 | 佐证：该设备节点处于**需要整机重启**才清的 pending 状态 |
| VISA（`ktvisa32`/`viOpen`）与 SICL（`iopen`）**两条独立通路同症状** | 二者共用 `ioGPIB` → 故障在**适配器接口层**，与上层 API 选型无关 |

**结论**：82357B 接口卡进入了**软件层无法自救的异常态**（跨进程、跨拔插存活），
唯一剩下的软件手段是**整机重启**；若重启后仍失败 → 按**适配器硬件**处理。

## 3. 本次事故暴露的代码缺陷（已在后续提交修复）

| # | 缺陷 | 状态 |
|---|---|---|
| 1 | burst 回读吃通用 120 s 超时 → 卡住时长时间握着设备锁 | ✅ 已修：`clamp(10 + 3×n×间隔, 10, 180 s)`，缺省间隔查 `TIMER?` |
| 2 | 失败路径**不收尾**→ 表留在流数据/SINT 输出 → 后续调用全废 | ✅ 已修：收尾 + `PRESET NORM` 放进 `finally` |
| 3 | 写命令撞上"表在流数据"直接失败 | ✅ 已修：`safe_write()` 恢复一次 + 重试 |
| 4 | 咨询锁过期被误当成"设备空了" | ✅ 已修：库接 `session_lock`，`connect()` 有他人占用即拒绝（`force=True` 出口） |
| 5 | **DLL 内部调用永不返回** → 句柄/接口无法释放（本次事故的真实卡点） | ❌ **未修**：见 §4 |

## 4. 仍未解决的根因与拟定方案

**根因**：`viOpen/viRead/viWrite` 一旦在 `ioGPIB` 里卡死不返回，Python 层的超时/`finally`/`viClose`
**全都执行不到**（线程卡在 C 调用内），接口被那个进程持续占着，直到进程被杀——但本次证明，
**光杀进程也不够**（适配器内部状态已坏）。

**拟定方案（按必要性排序）**：
1. **可杀死的 worker 子进程**：GPIB I/O 放到常驻子进程，父进程带**硬截止时间**等回复；
   超时即 `kill` 子进程（Windows 会强制回收其全部句柄）→ 重启 worker → 接口释放。
   —— 这是"卡在 DLL 内"唯一的工程解，也能让 MCP 不必重启、长采集不阻塞 AI。
2. **适配器节点重置出口**：把 82357B 纳入现有 `usb_reset`（PnP 节点重枚举，仪器固件/设定不受影响），
   作为"卡死后一条命令解开"的兜底。→ **暂缓为 TODO**（见 §9 B：本次实测 `pnputil /restart-device`
   要求重启整机，PnP 重置对该故障未必有效，等验证后再说）。
3. **运维铁律（已写进 skill）**：**咨询锁 ≠ 资源释放**。卡死后：先杀进程 → 再重置适配器节点 →
   仍不行就**重启整机**；在此期间**不要重试**（每次失败都会以访问违例结束，没有意义）。

## 5. 结论性备忘

* 3458A 本身没问题：`ID?`/读数/突发**都实测通过过**，故障在**适配器接口层**。
* 事故前的软件缺陷（超时过长、不收尾、无占用保护）**已修并有离线故障注入用例覆盖**。
* 剩余风险是**"DLL 内卡死"这一类不可中断故障**——需要 §4.1 的进程隔离才能根治；
   在此之前，**burst 仍是高风险操作**，建议在专用会话里做，且做完就重启/重置一次。

## 7. 追加定位：重启整机后"地址 9 没有仪器"的真因 = Talk Only 模式

重启 + 拔插 + 打开 Connection Expert 之后，软件链路全绿（驱动/枚举/`viOpen` 都正常），
但**地址 9 始终不应答**（`viRead` `TMO`/`RSRC_NFOUND`）。继续排查时发现：

```
ID?      -> '4.999981626E-01'
FUNC?    -> '4.999981272E-01'
RANGE?   -> '4.999983044E-01'
NPLC?    -> '4.999983414E-01'
ERRSTR?  -> '4.999982055E-01'
```

**每条命令都"回"一个电压读数**——手册 p.159 给出解释：

> `ADDRESS 31`（前面板设置）→ 表进入 **Talk Only 模式**：读数直接输出到 GPIB（给打印机用）、
> **`TALK` 指示灯亮**、**不理控制器**；地址存在**连续内存，断电不丢**。
> 退出：**按 Reset 键，或把地址设成 31 以外的值**。

这解释了全部现象：命令被忽略（所以"响应"是流数据）、`viWrite` 因表只在讲而超时、
控制器在该地址上找不到设备；也解释了**为什么重启这台表没用**（地址在连续内存里）。

**顺手确认的好消息**：那个读数 `4.99998E-01` 是**真实的电压测量值**（稳定到 ~1e-6），
说明 **3458A 的电压测量功能本身是好的**。

**处置**：前面板把 `ADDRESS` 改成 31 以外的值（如 9）即可退出 Talk Only；
`preflight --id` 现已能自动识别这一态（退出码 5）并打印同样的修法。

## 8. 结局（2026-09-23 收尾）与诊断修正

**恢复动作**：用户**重新拔插了 82357B**，并按了面板 **`Address` → 9 → `Enter`**（退出 Talk Only）。

**诊断修正（重要）**：§7 把"每条命令都回读数"直接归因为 Talk Only，**证据不足**——
该症状有**两个**成因，本次两个动作都做过、**无法完全分离**（用户回忆"可能是我按了按键
才有用的，而不是拔插 USB"，而拔插后我这边也确实测到过 `ID?` 恢复正常）：

| 成因 | 特征 | 处置（按此顺序都试） |
|---|---|---|
| **Talk Only**（前面板 `ADDRESS`=31） | **`TALK` 灯亮**、地址存连续内存（断电不丢）、表**不听**任何命令 → IFC/RESET 都送不进去 | **前面板**：**`Address` → `9` → `Enter`**（保留测量设定）或按 `Reset`（回到开机配置） |

→ skill 已按"**先看 `TALK` 灯按面板键，再做拔插**"的顺序写，并明确标注：
**Talk Only 无法远程退出**（别指望 `ks3458a_unstick`）。

## 10. MCP 侧"`viOpen` 访问违例"的真因 = 同进程两套 VISA（2026-09-23 定位并修复）

### 现象与定位过程

| 观测 | 结论 |
|---|---|
| CLI（`preflight --id`）一切正常；**MCP 里 `ks3458a_*` 全部报** `error_type=connection`、`access violation reading 0x0000000000000008` | 不是设备/适配器问题（同机、同一时刻 CLI 能读） |
| 给传输层加**步骤追踪**后报出：`viOpen(GPIB0::9::INSTR) @ ...\ktvisa32.dll: access violation` | 崩在 `viOpen`，且 DLL 路径正确 |
| 诊断快照（`_diag()`）对比：MCP 进程里 **`visa32=C:\Windows\system32\visa32.dll`、`ktvisa32=C:\Windows\system32\ktvisa32.dll`**；CLI 进程里系统 `visa32` **根本没加载** | MCP 长驻进程里被**别的仪器工具（pyvisa）**带进了**系统 VISA（IVI 壳）** |
| 复现实验：同进程先 `pyvisa.ResourceManager()` 再用 Keysight 通路 → `viOpen` 通过但 `viWrite` 报 `VI_ERROR_INV_OBJECT`；**两种加载顺序（先 Keysight / 先系统）都坏** | 两套 VISA 同进程**必然串味**，无法靠顺序规避 |
| 排除项：cwd、`VXIPNPPATH`、线程（主/普通/线程池）、`import server`（pyvisa 惰性）、DLL 路径选择均**不是**原因 | 唯一变量就是"进程里是否装了两套 VISA" |

### 修复

**把 3458A 的 I/O 挪进独立进程**（`keysight_3458a/worker.py`；父侧代理 `remote.RemoteDMM`）：

* 子进程只加载 Keysight 一代 VISA 栈 ⇒ 不再串味（MCP 侧 `ks3458a_status` 恢复 `ok:true`）；
* 顺带拿到"卡死可 kill"：调用超过 `deadline_s` 无响应 → `kill()` 子进程 → Windows 强制回收句柄；
* 子进程**不登记会话锁**（`INSTRUMENT_NO_SESSION_LOCK=1`），否则父进程会把自己人误判成"另一进程在用"；
* 回退开关：`INSTRUMENT_KS3458A_WORKER=0`（排障用；此时回到进程内，会把上面的老毛病带回来）。

### 教训（已写进 skill）

* **同一进程不要混用两套 VISA**（pyvisa 的系统栈 + Keysight ctypes 通路）——这不是"顺序问题"，是必坏；
* 长驻服务里跑"会加载第三方驱动的库"时，**默认就该进程隔离**：既躲 DLL 串味，也躲不可中断的卡死。
