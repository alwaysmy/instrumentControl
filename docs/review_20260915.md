## 二、A 类：安全护栏绕过（本次已修 + 回归）

三条都是"护栏写在了错误的层"：黑名单实现本身没错，但**不是所有下发路径都经过它**。

```python
# 修前 instr_query：唯一关卡是 "?" in cmd
if "?" not in cmd: return _err(...)
def fn(c): return {"response": c.query(cmd)}     # ← 从不调用 _is_forbidden
```
`c.query(cmd)` 会先把整串写下去再读，而 SCPI 允许 `;` 串联多命令，于是
`instr_query(res, "*RST;*IDN?")` 复位仪器后还能拿到正常的 IDN 回复（看起来成功）。
同理 `instr_write(res, "*IDN?", confirm=True, readback_cmd="*RST;*IDN?")`。
第三处是纯字符串匹配问题：`SYST:RES(?:E(?:T)?)?` 这类中间缩写（SCPI-99 §6.2.2 合法）
在只比对长短形式时漏网，实测 `:SYST:RESE`/`:SYST:PRESE`/`:SYST:COMMU:RLST RWL` 全部放行。

**修法**：黑名单改为**按 `;` 分段 + 助记符前缀匹配**判定（`_classify_forbidden` /
`_mnemonic`），`instr_query` 与 `readback_cmd` 要求**整条为纯查询消息**（判据＝每条 `;` 分段的**命令头带 `?`**；
注意早期实现误按"整段以 `?` 结尾"判，会把 `:MEASure:ITEM? VPP,CHANnel1` 这类标准查询一并拒掉，
已于 2026-09-15 按 SCPI 规范修正并补回归），
命中即 `forbidden` 并落审计。MHO 的 `:SYSTem:LOCKed`（屏幕/键盘锁定）一并纳入。
**回归**：`TEST_SCRIPTS/common/verify_remote_lock_block.py` 扩到 **47 用例全 PASS**
（含 6 条走私、11 条缩写、MHO 锁定族，以及不得误伤的 14 条放行用例）。

## 三、B 类：会写到错误位置的实现缺陷（已复核，未修）

### B1【高】DH1766 `safe_mode` 被复合命令旁路 —— 唯一能改**带电通道设定**的口子
`set_voltage/set_current/set_ovp/set_ocp` 都先调 `_guard_set(ch)`（第 186/210/255/276 行），
而 `apply_voltage()/apply_current()`（第 556-583 行，一次写全部三路）**从不调用它**：
```python
self.client.write(f"{C.APPL_VOLT} {values[0]},{values[1]},{values[2]}")   # 无 guard
```
`safe_mode=True` 的全部意义就是"接负载时不许改带电通道的设定"，一句 `APPL:VOLT` 即可绕过，
且写后回读会如实返回**已变**的值。建议：两个 setter 里对"值有变化的通道"逐个
`self._guard_set(n)`，或在 `safe_mode` 下 `any(get_output_state())` 直接拒绝。

### B2【高】SDS `acquire_depth(value)` 写出语法错误的命令
`commands.py:19` 的常量是查询形式 `ACQ_MDEP = "ACQ:MDEP?"`，而 `sds.py:206` 直接拼写：
`self.write(f"{C.ACQ_MDEP} {value}")` → 下发 `ACQ:MDEP? 1M`。手册里写形式无 `?`
（`ACQuire:MDEPth <memory_size>`）。**当前无调用点传值**（只在 `snapshot()` 里查询），
所以是潜伏缺陷；一旦有人传值，设备返回 `-113/-100` 而 `write()` 不查错，静默失败。
建议：加独立常量 `ACQ_MDEP_W = "ACQ:MDEP"` 并补 `SYST:ERR?` 校验。

### B3【高】DHO ASCII 波形分支是死代码
`dho.py:313` `fmt_up = fmt.upper()`，第 324 行却 `if fmt_up == "ASCii":`（混合大小写），
恒不成立 → 落到 `else` 抛 `ValueError: 不支持格式 'ASCii'（BYTE|WORD|ASCii）`——
报错信息还在推荐这个格式。手册明确有 `ASCii`（DHO800 手册 3.28.3）。改成 `== "ASCII"` 即可。
（同库的 MHO 版本无此问题，是 2026-09-15 新写的 `mho_control/mho.py` 的正确写法。）

## 四、C 类：验证工具链本身不可靠（"零猜测"的可信度问题）

### C1 【本轮已修】审计器结构性漏检 + 假阳性

> **修复摘要（2026-09-15）**：提取改为"AST 取字符串字面量（排除 docstring）+ f-string
> 还原 + 占位段支持"，归一化改为"段键元组 + 段内长短形式兼容 + 后缀路径命中"，手册索引
> 补上"无前导冒号的冒号链"（Keysight 提取版体例）与单段根命令（含 `:CLEar`/`:AUToset`
> 这类混合大小写）。效果：MHO 4 条稳定误报清零；SDS 41→109 HIT，并把此前**看不见的**
> `C{n}:VDIV/OFST/ATTN`、`TDIV?`、`TRDL?` 暴露成 MISS（正是 E6/E7 那批"实测可用但手册
> 查无出处"的旧别名）；Keysight 4→28 HIT。全仓 MISS 收敛到 **27 条且条条可解释**。
> 配套离线回归 `TEST_SCRIPTS/common/verify_audit_extractor.py`（60+ 断言，含全仓 MISS
> 基线：多一条少一条都 FAIL）。下面保留原始分析作为问题记录。
- **漏检**：`extract_cmds()` 只匹配以 `:`/`*` 开头的字符串字面量，因此 SDS 库里的
  `C{n}:VDIV?`、`TDIV?`、`TRDL?`、`ACQ:MDEP?`、`PRIN? BMP` 这类**常量根本不进扫描**
  （`sds.py` 只被抽出 7 条、`sdg_control/commands.py` 只抽 2 条）。B2/E3/E6 恰好都是
  这一类"审计器看不见的命令"。
- **假阳性**：`norm_head()` 逐段截前 4 字符，手册侧写全拼、代码侧写短形式时对不上；
  单段混合大小写根命令（`:CLEar`/`:SINGle`/`:TFORce`/`:AUToset`）因索引正则
  `:([A-Z]{3,8})(?![A-Za-z])` 整条不入索引——本次 MHO 的 4 条 MISS 全是这一类
  （逐条核对手册 3.1.1/3.1.4/3.1.5/3.2.1 均在，非猜测命令）。
- 提交的 `docs/command_audit_full_20260823.md` 已过期：重跑会重写它（2026-09-15 复跑
  产生 45 插入/19 删除），说明它自 2026-08-23 后再未随新命令更新。
**建议**：① 让提取器认得"任意字符串里的 SCPI 片段"（如同时匹配 `C{n}:VDIV?`、
`{ch}:OUTP?`）；② 建立**已知假阳性基线**，只对新增 MISS 报错（脚本返回非 0），否则
"零 MISS"永远需要人工重判；③ 报告改名去掉日期或每次自动更新并提交。

### C2 看门狗超时语义（已修一半语义）
`_guarded_call` 超时只说明"没等到回包"，命令**可能已送达**。旧代码在超时后仍无条件写
`executed=True` 审计；本次改为超时记 `executed="unknown"`，并在 `instr_write` 文档里写明
"命令可能已下发，请回读确认"。根因（挂起线程长期占用 `_DEVICE_LOCK`）见 D5，未动。

## 五、D 类：地址解析与连接管理

### D1【中】`canonicalize()` 用**子串**匹配 host（已实测）
```python
cached = _load_json(CACHE_FILE).get(kind)
if isinstance(cached, str) and host in cached:   # host in cached ← 子串！
    return cached
```
临时缓存 `{"dho": "TCPIP0::192.168.1.55::inst0::INSTR"}` 下的实测：
`canonicalize("dho","192.168.1.5")` → 返回 `.55` 的资源串；`canonicalize("dho","1.5")` 同样命中。
命中即"不联网直接返回"，**跳过 `*IDN?` 自证**；而 MCP 侧 `_verify_idn` 只比对 kind 匹配串，
**同型号两台仪器时校验会通过**——SCPI 就发给了另一台。这违背本仓库"地址必须自证身份"的核心原则。
建议：按字段比较 host（解析出 `TCPIP0::<host>::` 的 host 段做**完全相等**判断），
其余情况一律走"多协议探测 + `*IDN?` 校验"。

### D2/D4/D5 连接管理的三个同源问题
- **D4 会话泄漏**：`_sds()/_sdg()/_dmm()/_dho()/_mho()/_psu_connect()` 都是
  `connect()` → `_verify_idn()` → 抛错时**不关闭**已打开的会话；`_call()` 的清理只在
  `connect_fn()` 成功返回后才生效。DHCP 重新分配（IDN 不符）这条路径会每次泄漏一个会话，
  重试到耗尽仪器并发槽位。修法：连接函数里包 try/except 关掉再抛（`finally` 里关）。
- **D5 锁与看门狗不对称**：只有 3 个通用工具走 `_guarded_call`；34 个专用工具直接
  `with _DEVICE_LOCK:`，而 `_DEVICE_LOCK.acquire()` **没有超时**。一旦某个陈旧地址
  open 挂起（VXI-11 实测可无视 `open_timeout` 挂 2min+），后续**所有**工具都会卡在锁上，
  连 `instr_discover`（文档里的救火工具）也进不来。修法：`acquire(timeout=…)` 超时即返回
  错误而不是永久等待，或把专用工具也纳入看门狗机制。
- **D3** 已按上文修了审计语义。

### D6【中】真机实测：首次调用可能瞬时 `VI_ERROR_INV_OBJECT`
新写的验收脚本把 `import server` 放到 §7（此前只用库直连），第一次 `mho_status` 报
`VI_ERROR_INV_OBJECT (-1073807346): session or object reference is invalid`；之后 6/6 正常。
原因是模块导入会启动 `_prewarm_visa_rm` 后台线程，它"建一个 RM 再关掉"与主线程首次
`open_resource` 竞争。把 `import server` 提到文件顶部即消除（`verify_all_devices.py`
一直是顶部导入，所以从未暴露）。建议：`VisaClient.__init__` 对
`VI_ERROR_INV_OBJECT` 做一次 `sleep(0.2)` 重试，或让 `_prewarm` 完成后再允许连接
（现在 `_PREWARM_DONE` 事件已存在，只是只被 `_guarded_call` 用于放宽预算）。

  属"能跑但无手册出处"——`docs/feature_gap_20260909.md` 称其"手册明确有"不成立。
  建议二选一：改用有出处的写法，或在 `commands.py` 里注明"实测别名，手册未见"。
- **E8 写后不验证**：DH1766/SDG 的 `set_output` 写后不回读、不查错（同库的
  `set_output_all`/`set_output_mode` 却验证了），直接把库暴露给脚本时"被拒"看起来像成功。
- **F1**：`VisaClient.__init__` 中 `open_resource` 抛异常会泄漏 `self.rm`；
  长跑 MCP 进程反复探测离线地址会累积。`try/except: rm.close(); raise` 即可。
- **F3**：`find_device` 的层③对每个 ASRL 资源调 `identify()`，后者每次新建 RM——
  仓库自己记录过"每探测各建 RM 致原生层崩溃（8 串口实测）"，修在了 `instr_discover`，
  **没修** `find_device`/`identify`（`resolve()` 自动发现路径仍会走）。
- **F10**：SDG 负载门在 `actual == ""`（响应无 LOAD 字段）且调用方传空串时 `"" == ""` 通过；
  同库 DH1766 的 `_check_mode` 不会（空声明对比 `NORM` 会被拒）。
- **F11**：`_num("C1:VDIV 5.00E+00V") == 1.0`（实测）——只在 `query()` 未剥离头时暴露，
  而同库 `channel_coupling` 已记录过"发 `COUPLING?` 收 `C1:CPL`"这类头不一致的情况。
- **F12**：`SENS_COUNT=":SENS:COUN"`（手册是 `SAMPle:COUNt`）、SDG `BSWV_KEYS` 里的 `SQU`
  （手册用 `DUTY`/`SYM`）——两处零出处，未使用但应删或改。

## 七、复核为"非缺陷"（避免重复排查）

- `_is_query_only` 放行 `SYST:REM?`/`:SYSTem:LOCKed?` 是**有意**的（纯查询不改锁定状态，
  用于诊断面板是否被锁）；`*RST?` 之类仍被 `_FORBIDDEN_COMMON_RE` 前置拦下。
- `instr_write` 里 `json.loads(result)` 安全：`_call`/`_guarded_call` 所有返回路径都是
  `json.dumps` 产物（含 `_error("internal", …)` 兜底）。
- `detect_cidr()` 显式排除 `198.18.0.0/15`（代理 fake-IP 段）的写法正确。
- `_prewarm_visa_rm` 不 import 任何模块、重依赖留在主线程——刻意规避
  `mcp.run()` 与后台线程 import 互锁的历史事故，不是疏漏。
- DH1766 `_check_mode` fail-closed、`set_output_mode` 强制"输出全关"再动继电器、
  SDS `PREAMBLE_OFFSETS`（14 字段偏移/类型逐条对表 5-2）、`TDIV_ENUM`（39 档对表 5-3）、
  SDS 波形电压/时间换算公式、DHO/MHO 的 `(raw-YORigin-YREFerence)*YINCrement`——
  均逐条核对通过（详见文末验证口径）。
- MHO984D 真机事实：`*OPT?` **无响应**、`:CHANnel5..8` 无响应（仅 4 通道）、
  波形 ASCII 格式不带 TMC 头、无效测量哨兵 `9.9E37`——写驱动时不要引入 `*OPT?`。
